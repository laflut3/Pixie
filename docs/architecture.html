How it works

Follow the request.

A compact feature map of the current Rust implementation, from startup to response.

The request path

  1. Configuration

    main.rs loads YAML and resolves the listen address, workers, and optional TLS files.

  2. Connection acceptance

    server.rs binds a TCP listener and sends accepted connections to the worker pool.

  3. TLS handshake

    With TLS configured, rustls validates credentials and optionally authenticates a client certificate before HTTP parsing.

  4. HTTP parsing

    The handler reads bounded headers, validates the HTTP version and Host, and accepts GET or HEAD.

  5. Route and file

    The router maps a simple page name to an HTML file under the selected web root.

  6. Response

    The handler writes a status, content type, content length, and body, then closes the connection. HEAD omits the body.

Feature: configuration

src/config.rs parses YAML with serde. Compiled defaults cover missing values. An explicit TLS section requires a certificate and key. Configuration is loaded once at startup. See the complete option reference.

Feature: static routing

src/router.rs chooses the web root and appends .html to a valid page name. The home page is hello.html. Query strings do not change the selected file. Paths with separators, encoded characters, or dot segments are rejected. Files are read as UTF-8 text on each request.

Feature: HTTP/1.x

src/server.rs supports HTTP/1.0 and HTTP/1.1 requests. It requires Host for HTTP/1.1, limits request headers to 8 KiB, and sets five-second socket read/write timeouts. These are per-I/O timeouts, not a total request deadline. Connections close after one response.

Keep-alive, caching validators, ranges, compression, uploads, HTTP/2, and HTTP/3 are not implemented here. HTTP/1.2 and HTTP/1.3 are not standardized versions.

Feature: TLS and mTLS

src/tls.rs loads the PEM chain and private key into a rustls server config. Without a client CA it authenticates the server only. With a client CA it uses WebPkiClientVerifier to require a trusted client certificate. Credentials are loaded once, and handshakes run within connection workers.

Feature: worker pool

src/threadpool/ holds a fixed set of worker threads fed by a channel. Each connection occupies a worker while being handled. The job queue is unbounded, so worker count is a concurrency setting rather than a complete overload limit.

Feature: logging

src/logger.rs sends info, warning, and error messages to stderr. Startup logs show the address, worker count, TLS mode, and web root. There is no structured per-request access log or metrics endpoint yet.
